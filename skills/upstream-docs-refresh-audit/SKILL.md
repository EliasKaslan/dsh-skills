# 上游文档缺口核查

## 何时调用

**触发**：这批需求有文档吗 / docs要刷新吗 / 参数主线有没有 / 内部代号叫什么 / 导航漏页面了吗。

**转交**：启动推理服务见 [ascend-vllm-serve](../ascend-vllm-serve/SKILL.md)。

**前置**：恢复当前任务目标、输入与范围；缺少必需证据时如实标明。**后继**：交付可追溯结果与未覆盖项；编写或调整skill契约见 [dsh-skill-authoring](../dsh-skill-authoring/SKILL.md)。

固定需求原件、目标仓SHA、文档范围、用户语言和交付范围（审查/方案/实际编辑）。已有明确范围就执行，只有影响结论且无法恢复的缺项才问。对本地checkout、工作树和远端ref分别记录，不能fetch后仍把旧HEAD称“最新”。保留用户工作；只读审查可直接用git对象，不强制建全新worktree。

从原件抽取模型/内部代号、硬件、精度、功能、每条env/flag、约束和证据。缺失的代码块/实验字段记录缺失，不从标题补出命令；TXT导出不一定丢代码，需看实际格式。建立带依据的代号/公开名称/类或参数映射，词面零命中时看别名、生成配置、提交记录和真实调用，不据此立即判不支持。

分别核对代码行为、发布承诺与用户可发现的文档。主文档、README、生成导航/标题hook、locale与发布站点的生效关系依目标仓构建逻辑确定；nav_titles.py不是跨项目“唯一权威”。多语言/硬件tab先定位上下文，同一型号不同tab、量化或场景可能有不同值，不能只摘一行拼冲突。

对输入中的每个启动开关查当前parser/env注册及caller，区分字面同名、语义等价、已废弃、仅内部支持和未知。grep命中只证明文字存在，代码属性名可能与CLI不同；无匹配也需说明搜索范围和动态注册边界。不能无条件以转测参数裁决主线值：长上下文支持、推荐值与某次实测配置可能都是不同口径。

每条需求交付：用户目标、映射依据、代码/文档状态、最小刷新位置/内容、依赖与未确认项。刷新建议不引入未确认开关；实际编辑只在用户要求时完成。大任务可分项取证，但不强制N需求=N代理、固定六节或分三次写盘。汇总时复核冲突并可用更强证据改判，保留理由；不禁止汇总者纠正findings。

与上一轮比较仅在有真实旧产物时做，说明基线/输入变化及重判原因。交付引用绑定SHA和符号/节标题；“通过”来自本轮实际检查，历史行号/计数不继承。

来源：DSH upstream-docs-refresh-audit及4份reference，2026-11-16整理。固定路径、主线SHA、206个locale和12条需求等只属于历史案例，未迁为当前事实。

## 多级表头的支持矩阵：按二级表头取列，别目测

## 多级表头的支持矩阵：按二级表头取列，别目测

支持矩阵常见「一级分组 + 二级子列」两行表头，且数据行的单元格数往往比一级表头多（分组列被跨度占位）。例如某张表一级写 `| Graph Mode |||| Npugraph_ex ||`，二级才给出真正列名 `PIECEWISE | FULL_DECODE_ONLY | FULL | FULL_AND_PIECEWISE | Static kernel | Super kernel`。此时：

- 按一级表头切片或肉眼数竖线一定错列；必须解析二级表头（`^^` 是上一级合并单元格的占位符），用子列名定位目标格子，改完再按同一表头回读该行各格值确认没串列。
- 同一概念在不同硬件 tab（`=== "A2/A3"` / `=== "950PR&950DT Products"` / `=== "Atlas 300I DUO"`）里可能用不同列名（新表叫 `Graph Mode` 四子列，旧表仍叫 `Piecewise ACLGraph / Fullgraph ACLGraph`）。先确认目标表自己的列名与图例，再按该表的写法改，不要跨表统一措辞。
- 先读图例再改值：`✅ Supported（已实现并验证）` / `🔵 Experimental` / `🟡 Unverified（代码已合但未系统测试）` / `❌ Unsupported`。把 🟡 改成 ✅ 需要「系统测试」级证据——SIT/nightly 配置里真实带了该参数、e2e 用例实际跑该模式；只有代码路径存在或教程示例写了，不足以支撑 ✅。反过来，教程已经给出该模式的启动命令而矩阵仍标 🟡，就是可复现的内部矛盾，属于最小刷新的好目标。
- 一个模型可能在多张硬件表里出现，也可能在某张表里根本没有行（例如只有 300I DUO 表有、A2/A3 与 950DT 表没有）。先按模型名把全部出现位置列出来，再决定"改哪些格子"；没行的地方谈不上刷新，要在交付里说明，别默默补一行。

翻译文件不要凭感觉改：先看目标仓的定时翻译 workflow（cron 触发的 po 生成/翻译/开 PR 步骤）和 po 抽取脚本。若抽取脚本显式跳过"含 ✅/❌/纯数字的数据表格行"，则矩阵数据格本就不进 gettext，PR 只改英文 `.md`，手改 `.po` 只会被下一轮覆盖。

## 刷新粒度：写支持范围，不搬实现细节

## 刷新粒度：写支持范围，不搬实现细节

用户指南里的能力陈述写到「支持范围」就够——模型、硬件、模式（例如「A3 与 A5 支持」）。算子名、workspace、错误码、内部开关属于实现细节，默认不要写进用户文档，除非用户明确要求；写深了大概率被要求回退重写。

不要为同一件事在相邻页面再加一条指针（哪怕只有一行）。单一落地、其余不动；cross-link 等用户点名再加，否则就是多余 diff。

动笔前先确认粒度：同一事实常有多层口径（四个子列 × 多张硬件表 × 已支持硬件清单），先问「刷哪些格子、写到什么程度」，比写完被打回两轮便宜。

撤掉已经推送的改动（某个文件不该改）时，把工作树退回基线而不是叠一个新提交：

```bash
git reset --soft HEAD~1          # 保留改动到索引
git checkout <base> -- <path>    # 该文件整体退回基线
git reset && git add <kept-path> && git commit -s -m "..."   # 只提交该留的
git push --force-with-lease=refs/heads/<branch>:<old_sha> <remote> <local>:refs/heads/<branch>
```

只对自有 PR 分支这么做；交付里说明「已改写历史」「旧 head → 新 head」，别让 reviewer 拿旧 sha 对不上。判断依据是 `git diff --stat <base> HEAD` 的文件数，不是提交数。

## 图模式取证：Runtime Mode 不等于 cudagraph_mode

## 图模式取证：`Runtime Mode` ≠ `cudagraph_mode`

引擎 CUDAGraph Stats 的 `Runtime Mode = FULL` 是"重放了被捕获的整图"，不是 `cudagraph_mode=FULL`；`cudagraph_mode=<...FULL_DECODE_ONLY...>` 与它可同时出现。据此写"支持 FULL"会被评审打回。

- 边界：`FULL_DECODE_ONLY` 只捕 decode 整图；`FULL` 让 prefill 也进图；`FULL_AND_PIECEWISE` 只覆盖 decode 半边，不能替代 FULL；BI 用例常走默认 mode。
- 升级矩阵格子前，先在 tests 里找显式设置该 mode 且开 `VLLM_BATCH_INVARIANT` 的用例；没有 mode × 硬件实测就保持 🟡。
- capture 行、吞吐跃升、Runtime Mode 计数只证明"图在跑"，不证明策略与 prefill 入图；实现无 gating 也不等于已验证。
- 文档声称某 mode 而矩阵仍 🟡 会被当成矛盾；收窄措辞优于抬高矩阵。
