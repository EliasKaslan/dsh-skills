# 漏洞报告核验

## 何时调用

**触发**：这个高危是真的吗 / 行号对不对 / 注入能用吗 / 定级高不高 / 有没有漏报。

**转交**：仅审文档扫描分数见 [aidd-report-reader](../aidd-report-reader/SKILL.md)。

**前置**：恢复当前任务目标、输入与范围；缺少必需证据时如实标明。**后继**：交付可追溯结果与未覆盖项；编写或调整skill契约见 [dsh-skill-authoring](../dsh-skill-authoring/SKILL.md)。

固定报告原件、明确的代码SHA/依赖/部署配置、审查范围及可执行验证边界。报告只有日期时，把最近提交当候选而非已证明基线：提交时间、分支与实际部署可能不同。基线无法恢复则说明不确定性，分别审查历史候选与当前代码。

对每项还原source→验证/转换→sink→执行上下文：谁控制哪部分输入、是否跨信任/权限边界、调用与参数是否可达、现有防护实际生效、影响是否成立。grep只见定义不证明不可达，插件注册、反射、生成代码、CLI入口和外部库回调也可能调用；静态无法闭合时保持待验证。

CLI argv/本机环境变量可能来自不可信文件、CI配置或低权限用户，不能一概归为自伤。反之输入来自PR/网络也不自动高危，要看运行权限、secret暴露、交互与上游控制条件。追到具体主体和数据来源后，用任务约定的severity/CVSS版本评估；防护/攻击复杂度分别解释，避免“无hash+TLS开就低危”“TLS关就高危”的固定映射。

源码点名文件未变化不能证明漏洞未漂移：caller、验证层、依赖、构建/部署与权限也需重核。用可达性证据区分“存在危险代码”“可达缺陷”“PoC复现”“目标环境可利用”，注明未运行项。修复后同时回归攻击输入与合法功能，不接受仅改报错文本。

供应链下载核查TLS实际配置、CA/主机验证、不可变版本和制品hash。CMake需结合版本与作用域：3.31起CMAKE_TLS_VERIFY默认ON，旧版默认OFF，变量/环境/每调用参数还能覆盖。TLS验证和制品完整性目的不同；固定hash只适用于同一字节制品，不给不同分支URL一律填同一hash。参考 [CMake官方说明](https://cmake.org/cmake/help/latest/variable/CMAKE_TLS_VERIFY.html)。

在已授权源码范围内按同类sink/调用链扩展核查，记录覆盖范围，不能因抽查几处写“无漏报”。报告编号缺口可能是预留/删除/合并，先对交付manifest再判丢条目；等级前缀也以该报告命名约定为准。

报告逐项给：基线与漂移、可达路径、控制主体/前置条件、防护和剩余影响、证据等级、修复状态、未覆盖项。复现实验使用本地合成数据或授权隔离环境，不把审查扩展成对未知外部目标的利用测试。
