# 核实第三方漏洞扫描报告

核实的是**「这条漏洞在真实代码路径上是否可达、谁能触发、定级是否合理」**，不是「报告里有没有这段代码」。

## 何时调用

**加载本 skill 当：**
- 用户丢来一份或一批漏洞扫描报告（常见九节模板：风险影响 / 根因 / 证据链 / 利用场景 / 影响范围 / PoC / 修复 / 验收 / 证据边界）并说「核实一下 / 看看是不是真的」。
- 报告带时间戳或 commit 基线，要回答「结论现在还有效吗」「这条到底高危还是自伤」。
- 要判「有没有漏报」「定级合不合理」「PoC 真跑过没有」「交付清单全不全」。

**不要用本 skill（转交）：**
- 对象是前代 agent 产物目录的完成度 → 用 `prior-agent-artifact-audit`。
- 对象是论文声称 / 开源复现 → 用 `arxiv-paper-deep-read-and-claim-verification`。
- 任务要拆解、并行派发、校验子代理结论 → 用 `orchestrating-subagents`。
- 本机 pwsh 的编码 / 行数 / 计数 / 隐藏目录坑 → 用 `pwsh-on-windows`。
- 定级结论要落盘成 skill → 用 `sedimenting-skills`。

**前置**：能访问被审仓库的 git（至少要有与报告时间戳匹配的历史 commit）；报告里写明了「文件:行」。／ **后继**：逐条结论汇总成核实报告，每条断言标证据形态（命令 / 文件:行）。

## 0. 一条总口径：行号真实 ≠ 数据流真实

报告的行号命中只证明「这段代码存在」，不证明「能被触发」。每条结论必须过四关，缺一关就不能写「成立」：

| 关 | 要回答 | 不过关长什么样 |
|---|---|---|
| ① 主位置命中 | 报告指的文件:行真是那段代码吗 | 行号是编的 / 基线选错 |
| ② 可达性 | 这行在 CLI / 服务路径上吗 | 死代码、无调用点 |
| ③ 上游门 | 载荷真能到 sink 吗 | 上游校验 / 早退挡死 |
| ④ 威胁模型 | 谁能控制这个输入 | argv 自伤被写成远程可利用 |

定级放在 ④ 之后做（§5）。**四关全过才叫「漏洞成立」；只过 ① 只能叫「代码存在」。**

## 1. 先锁基线，再判漂移（不要在当前 master 上直接核）

报告是历史快照。先把报告时间戳落到与之匹配的 commit，再和当前主线比差量。

```powershell
# 报告时间戳 → 最接近的历史 commit；多副本/多分支时按提交日期比，选最接近的那个
git log --before='<报告时间戳，如 2026-10-31 10:31:37>' -1 --format='%H %ad %s' --date=short
```

```powershell
# 被点名的文件有没有漂移
git fetch origin
git diff --name-status <基线commit>..origin/master -- <报告点名的文件>
```

判读：
- **空输出 = 未漂移** → 在该基线上复验，结论仍然成立。
- **有 M/D/A = 漂移** → 只在漂移的文件上重验，再分别写「仍存在 / 已修复」。
- 措辞分三档：未漂移且复验成立 / 漂移但复验仍成立 / 漂移且已修复（原结论失效）。

## 2. 第一步：主位置批量命中（最便宜的分诊）

每份报告的「主位置 / 关联位置」都是「文件:行」。一条循环把每行原文打出来，比逐个读文件便宜一个数量级。

```powershell
# positions.txt 每行 = 报告主位置的「文件:行」（用仓库相对路径）
foreach ($x in (Get-Content .\positions.txt -Encoding utf8)) {
  $p,$n = $x -split ':',2
  "{0} -> {1}" -f $x, ((Get-Content $p -Encoding utf8)[[int]$n-1])
}
```

- 用**仓库相对路径**：绝对路径的盘符冒号会被 `-split ':'` 拆错。
- 读文件必须 `-Encoding utf8`，否则中文行内容错位且不报错 → 见 `pwsh-on-windows`。

判读：**全部命中 → 报告没编行号**（但只能停在这一步之后，继续 §3）；**未命中 → 先怀疑 §1 基线选错**，再判报告行号失准。

## 3. 三种必须回溯的真实性（行号对了也照样是假漏洞）

| 回溯 | 查法 | 不过关的判据 |
|---|---|---|
| 可达性 | `git grep -n '<sink 所在函数名>'` | 命中只有 `def` / docstring，**没有任何调用点** → 该函数不在任何执行路径上 |
| 上游门 | 顺着 sink 的每个插值/参数往上游追到第一个能决定「它能不能到拼接点」的分支 | 上游 `importlib.import_module` + `getattr` 取不到属性就早退、白名单、`if not x: return` → 载荷到不了 sink |
| 张冠李戴 | `git grep -n 'def create_.*' -- <文件>`，再 grep 各生成器名的调用者 | 同文件里有同族生成器 `create_X` 与 `create_X_for_Y`，报告把 A 的写盘链挂到 B 的注入点上 |

```powershell
git grep -n '<函数或生成器名>' -- <文件或目录>   # 看是否只有 def、看谁在调
```

- **用 `git grep` 而不是默认文本搜索**：工具默认跳过隐藏目录（`.github/`、`.gitcode/`），而 CI 攻击面恰好都在那里 → 详见 `pwsh-on-windows`。
- 三种回溯的结论要分开写：「行号命中」「可达」「上游未挡」「归属正确」是四条独立断言。

## 4. 威胁模型单独判：自伤型 vs 真攻击面

在定级之前先回答一句：**谁能控制这个输入？** 依据是输入来源，不是「有没有字符串拼接 / 有没有 shell」。

| 输入来源 | 谁能控制 | 典型判定 |
|---|---|---|
| CLI 参数、本机环境变量、马上要执行的自家脚本内容 | 受害者自己 | 自伤型 → 低危或撤回 |
| 未认证 PR / issue / 分支名等第三方提交内容 | 任意第三方 | 真攻击面 → 高危 |
| CI 工作流下载的远端文件、上游仓库 | 源站 / 域名 / 上游维护者 | 真攻击面（供应链）→ 再过 §5 校准 |
| 网络响应、队列消息、远端服务返回 | 上游服务 | 真攻击面 |

- **写结论时必须点出「攻击者可控来源」的具体一条**；点不出来就降级或撤回。
- 自伤型的组合判据：所有插值源都来自受害者自己的 argv，且全树不存在 CI / 队列 / 网络输入路径。

## 5. severity 校准看「防护是否已经存在」

同一个缺陷，周围已有的防护决定它是高危还是可接受：

- **无 hash + 走 HTTPS + TLS 校验默认开启** → 攻击面只剩源站投毒 / 域名劫持；无 hash 只损失可审计性 → **降级**。
- **TLS 被显式关掉（`SSL_VERIFY off` 之类）+ 无 hash** → **维持高危**。
- **同目录已有正确范式**（别的同类文件写着 `URL_HASH SHA256=...`）→ 证明这是**局部疏漏**而不是「技术上做不到」，既能当负向对照，也能据此要求统一修复。

## 6. 判「漏报」要普查同类文件，不能只验点名处

```powershell
git grep -n -E 'URL|URL_HASH|SSL_VERIFY|TLS' -- '<同类文件所在目录>'
```

- 按**同一判据逐文件填表**（有没有 hash / TLS 开还是关 / 有没有校验），得「实得数」。
- 实得数 > 报告点名数 → 漏报；漏掉的那个可能更严重（同样缺 hash 还额外关了 TLS）。
- 只核报告点名的两处就写「无漏报」，是这类任务最常见的错。

## 7. 必查报告的自述证据状态

- 好报告会自己标：`NOT_RUN` / `SYNTAX_CHECKED` / 「已实际执行」。
- **把两件事分列记**：「技术事实是否成立」（§2–§5 自己验的）与「PoC 是否真跑过」（照抄报告自述，标【文档】层）。
- 报告写 `NOT_RUN` 的，不能当已验证结论用；**没写证据状态的，按「未验证」处理**，不按「已验证」处理。

## 8. 交付完整性单独查（与漏洞内容无关，但影响可用性）

```powershell
git grep -ohE '\b[HML]-[0-9]{4}\b' -- '<交付目录>' | Sort-Object -Unique
```

- **编号有空洞**（整段缺号）→ 报告缺条目，结论面不完整。
- **ID 前缀与标称等级矛盾**（`L-` 前缀标中危）→ 定级体系没对齐。
- **关联字段用了另一套编号** → 交叉引用断链，逐条对不上。

## 9. 坑与修法

- **「主位置命中」当「漏洞成立」** → 行号真实不等于数据流真实。修法：§3 三关逐一过，分开写断言。
- **只在当前 master 上核历史报告** → 既可能核到已修好的代码，也可能把新代码的锅算到旧报告上。修法：§1 锁基线 + 差量。
- **只看点名文件判漏报** → 修法：§6 同类文件全量填表，给「实得数 vs 点名数」。
- **把「技术事实成立」写成「漏洞已复现」** → PoC 没跑过就是没跑过，§7 分列。
- **在自伤型输入上写「攻击者可注入」** → 威胁模型先判，§4 要能点出可控来源。
- **直接转述报告 severity** → 定级必须过 §4 + §5，并写明升降级理由。
- **用默认文本搜索查隐藏目录** → `.github/` / `.gitcode/` 被跳过，CI 攻击面直接漏掉；用 `git grep` 或 `Get-ChildItem -Force -Recurse`（细节见 `pwsh-on-windows`）。
- **读源码不带 `-Encoding utf8`** → 行内容/行号错位且不报错（见 `pwsh-on-windows`）。
- **报告自证矛盾还当基线**（声称某文件 N 行、又引用 >N 的行号）→ 整份降级为线索，只认自己复验的结果；档案级取证的通用做法见 `prior-agent-artifact-audit` §3。

## 10. 不要做什么

- 没锁基线就写「已修复 / 仍存在」。
- 把「行号命中」当独立结论条凑数。
- 把自伤型写成远程可利用，或把未认证 PR 的自伤写成高危。
- 因为报告写了 `NOT_RUN` 就否定技术事实（两者独立）。

## 11. 验收标准

1. 每条漏洞都给出：基线 commit + 漂移判定 + 主位置命中 + §3 三关结论 + §4 威胁模型归属 + 校准后等级。
2. 漏报普查有「实得数 vs 报告点名数」两个数字与逐文件判据表。
3. 报告自述证据状态单独成列，`NOT_RUN` 项未被当成已验证。
4. 交付完整性三项（编号连续性 / 前缀与等级一致 / 交叉引用同一套编号）各有结论。
5. 每条断言带证据形态：命令、文件:行，或报告原文引用。

## 12. 实测样例（一例，仅示意形状，不代表任何具体仓库）

一次 7 份同模板静态扫描报告的核实：主位置符号全部命中；但其中一条的 sink 所在函数全文件只有 `def` 与 docstring、无调用点 → 判不可达；另一条的注入点被上游 `getattr` 早退挡死 → 载荷到不了拼接点；两条高危都能追到攻击者可控来源（CI 下载链、未认证输入）；一条中危的三处插值全部取自受害者 argv 且全树无 CI / 网络输入 → 判自伤并降级；同类文件普查多出 1 个报告未提、且额外关掉 TLS 的同类缺陷；交付层面查出编号整段缺口与前缀-等级矛盾。
