## 什么时候写入

适配完成后归纳案例；中途形成已证实机制或有价值的失败反例也可写入，但状态明确为 PARTIAL/FAILED/HYPOTHESIS，不能伪装为完成案例。用户要求更新 knowledge 的授权不包含发布到远端仓库或传出私有模型/数据。

优先使用 [case-template.md](case-template.md)。它规定信息语义，不强制字段顺序或文件格式。每个结论区分：

- **已观测**：具体输入、环境和结果，可定位原始工件。
- **已归因**：同输入对照或消融支持的机制，附排除范围。
- **候选方法**：新任务可试的办法及前提。
- **未覆盖/失效条件**：不能迁移的范围。

## 维护约定

1. 使用稳定、可读的案例文件名，索引增加症状/算子/芯片/框架标签和范围。先检索相似条目，避免同一结论反复复制。
2. 绑定模型几何、精度、硬件/软件与实际加载实现；记录工件相对路径、不可变版本或 SHA。大数据和权重留在任务归档，knowledge 只存足以检索与理解的摘要。
3. 因果证据不足时保留假设措辞。shape 敏感的观测不能升级成“某芯片的某 kernel 总是如此”；低精度、特殊 token、多模态和稀疏截断分支独立标覆盖。
4. 成功与失败候选分开，列出哪些结果因新源码/环境而失效。新版本推翻旧结论时保留原范围，标注新证据并双向关联，不悄悄改掉历史结果。
5. 多个独立案例支持同一机制后，才考虑抽到 references；抽象成适用条件与方法，不抽成固定模型/框架/设备/日期的操作指令。单例中的固定数值仍留在案例。
6. 不保存密码、密钥、连接凭据、私有对话或无必要的个人标识。保留复现所需的代码/环境指纹，路径用归档内相对路径或说明性标识。
7. 写完检查相对链接、状态、来源、证据可获得性和未覆盖项；若原始工件不可获得，标明仅保留历史摘要，不能宣称当次重新验收。

后续 agent 使用某案例修复新模型后，应新增本轮案例并更新索引，说明沿用了什么、哪些前提不同、原方法在哪些 shape/拓扑上失效。不要只往旧文档追加“也适用”。
