# 跨框架机制支持度调研

## 何时调用

**触发**："某机制在哪些框架/模型被支持""业界有没有同类做法""这几家实现的是不是同一件事""X 到底叫什么"。
**不适用**：只查单个框架某个 API 怎么用 → 读它的文档；只做版本树差异 → 转 tag/commit 差异类技能；只核实某个 PR 是否合入 → 直接看 `merged_at`。
**前置**：先把被调研机制的**契约**钉住（参数名、维度、约束），否则各家说法无法对齐。
**后继**：结论必须区分"实现了"与"被采用"，并给来源分级。

## 先做术语对齐，再谈支持度

目标词若只在自家源码命中、其它框架 **0 命中**，它就是**自造术语**——此时"搜不到"不代表"没人做"，而是大家用了别的名字。先列出各家叫法再答支持度。实例：同一概念分别叫 `tokens_per_state`、`index_kpool`、`compress_ratio`，而提问用的名字只在一处出现。

## 判"是否同一机制"只看结构量，不信名字

选一个可机械验证的结构量当判据（如"页内行数是否等于 `block_size / N`"），逐家去比。名字会骗人：同名参数可能一个是**真存储粒度**、另一个是**值级聚合并寄生在行尾列**，按名字去索引会读到相邻字段。

## 把同名概念分层

至少分三层，否则会把三种东西混成一种：

- **L1 存储粒度**：一个存储单元覆盖多个原始 token（页内行数减少）。
- **L2 值级聚合**：存储布局不变，多算一个聚合值塞进已有行。
- **L3 选择粒度**：存储完全不变，只是"按粗粒度选、再展开到细粒度"。

判据：看**存储布局/行数**变没变，不看有没有 "pool/compress" 字样。

## 分清"实现"与"被采用"

- 有 API ≠ 有人用：查**调用方**（本仓 grep + 下游仓），0 调用方要明确写出来。
- 有实现 ≠ 已发布：查 tag / release / wheel 是否存在。
- 框架支持的是**通用机制**还是**该模型专用路径**必须分开说；通用机制不代表这个模型已接入。

## 实现与论文/文档的自检

核对声明与实际是否等价。典型偏差：论文"逐元素算完再取极值"，实现改成"先聚合再算"，而 `max(⟨q,k⟩) ≥ ⟨q, mean k⟩` —— 这是**近似**，不是等价重排，必须标注，别在结论里说成"同一种东西"。

## 取证路径（配额友好）

- GitHub **代码搜索 API 需认证**，用不了 → 改用 `git/trees?recursive=1`（每仓 1 次）落临时文件再本地 grep；树可能数 MB，**别把 JSON 打进上下文**。
- 固定路径用 `raw.githubusercontent.com` 探测（看状态码），不耗 API 配额，且能证明"当下"状态。
- 本地已有克隆优先；`git grep` 全部分支，但先 `fetch` 再用 `origin/<branch>`（本地分支常落后，直接 grep HEAD 会假阴性）。
- 来源分级：**代码可验证 > 官方文档 > 二手报道**；未上机、未读到原始出处的标 `未验证：`。

## 常见坑

- 检索词过泛：`pool`/`compress` 会捞回显存池、量化、驱逐，必须加限定词或直接按结构量检索。
- 只查一个分支：同仓其它分支实现可能不同，结论要写明"哪个分支上有"。
- 把"框架通用机制"写成"该模型支持"——最常见的夸大。
- 拿二手博客当原始出处；找不到原始报告就明说找不到。
