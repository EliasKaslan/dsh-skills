# 网页可读性：用真浏览器逐节点测对比度

## 何时调用

- 触发信号：用户说"字看不清 / 和背景太接近 / 浅色主题读不了 / 标题几乎看不见"；或任何"换主题后配色不对"的反馈。
- 边界：只负责**测量与定位**具体元素与色值；具体改哪个色由项目自己的 token 决定。
- 后继：改完必须用同一套测量复测，给出前后比值。

## 不要靠肉眼调色，先在真浏览器里量

在页面里跑一段脚本，遍历带自有文本的节点，取 `getComputedStyle().color` 与**实际有效背景**，
按 WCAG 算 `(L1+0.05)/(L2+0.05)`：正文 < 4.5、大字（≥24px，或 ≥18.66px 且 600 字重以上）< 3.0 即不合格。
输出按比值升序排列的 offender 列表（类名 + 色值 + 字号 + 比值）——这就是改色的唯一依据。

**测前必须先确认主题真的生效**：同时打印 `document.documentElement.dataset.theme`
与 `--text` / `--bg` 的 computed 值。若 `data-theme` 已是 light 但变量还是深色值，
说明后续渲染把它改回去了，这次测量无效。让应用自己切主题
（例如 `browser.newContext({ colorScheme: 'light' })` + 应用默认 `auto`），
不要在渲染后手动改 `dataset.theme` 并立刻测量。

## 三个会给出假结论的坑

1. **渐变背景不进 `backgroundColor`**：白字压在渐变蓝按钮上会被算成"白字压页面底"（比值 1.08 的假阳性）。
   遇到祖先 `backgroundImage !== 'none'` 就跳过该元素，别去修它。
2. **半透明背景必须合成**：`rgba(...,.1)` 的柔和底色若被当成"无背景"直接落到页面底色，
   会放大或缩小真实比值。按 alpha 与页面底色合成后再算。
3. **`color` 常常是继承来的**：元素自身没声明颜色时，问题在**继承根**，不在它。
   所以修的顺序是：继承根（body / 外壳容器）→ 主题 token（`--text-2` / `--text-3`）→ 个别按钮。

## 一个高频根因：两层样式各说各话

"外壳层（chrome）+ 应用层"两套样式并存时，常见的是：
应用层用主题变量（`--text` / `--surface`），而**外壳层把颜色写死成某一主题的值**
（例如 `body { background:#070b16; color:#e6ecff }`）。切到另一主题后，
应用层卡片变白、文字却从外壳继承了近白色 → "白底白字"，标题几乎不可见。
判据：`getComputedStyle(document.body).color` 与 `--text` 的值**不一致**，基本就是它。

## 改完要复测，注意构建产物

改的是源 CSS 时，先把构建产物（`docs/` 之类）重建再测，否则测到的仍是旧样式，
会得出"改了没用"的相反结论。复测时按元素逐个点名（`.stat-value` / `.conn-text` …），
给出"改前 → 改后"的比值表，而不是只说"已修复"。
