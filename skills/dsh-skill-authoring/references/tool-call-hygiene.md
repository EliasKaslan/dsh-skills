# distill_skill 入参失败与核对（细则）

正文只留四条自查，完整失败样本与修法在此。

## 一、预算类拒绝

回执形如「正文 N 字节，超过热目录上限 8000」与「N 个 ## 段，超过上限 8」，并给出当前值。

- 净增公式：新 body 字节 ≤ 8000 − 现有字节 + 被替换章节字节。估算不准时只做减、不做增。
- 多次超限说明把长内容留在正文了，应整段移入 references，正文只留一行指针。
- 段数超限最常见的原因不是内容多，而是标题重复，见下条。

## 二、段数 +1 的隐性原因

`title` 参数已生成 `## <title>`。若 body 第一行又写 `## 同名`，段数 +1，在 8 段上限下立即被拒。
body 不要自带一级 `##` 标题，直接从正文开始写；需要子结构时用 `###`。

## 三、JSON 手写坏

错误原文（注意原报错里用的是单引号）：Expected ',' or '}' after property value in JSON at position N。

- position 通常落在最长那个字符串内部，即 references 的 content。
- 两大根因：字符串里出现未转义的 ASCII 双引号；字符串里出现原始换行（未写成 \n）。
- 写法约定：正文与 references 内容一律不用 ASCII 双引号，中文用「」；全部换行写成 \n；整份入参保持单行。
- 同批内容出现 U+FFFD 替换字符时视为序列化已被破坏，整段重写而不是局部修补。

## 四、回执核对（必做）

`mode=replace` 的回执可能仍打印旧章节名（实测两次），说明 title 与 targetSection 的改名行为不一致。
落盘后立即 grep `^## ` 看实际标题；不一致就用 edit 改名，改名后再读一次确认字节数未变。
