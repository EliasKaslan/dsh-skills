# 对抗式复核清单（批量文档修复）

复核者约束：只读、不改产物、不 commit；每条给 `file:行` 或 commit 号；结论落在「一致 / 不一致 / 证据不足」三档。

## 四路分工

1. **事实**：API 签名、返回值、公式、表格数据 vs 实现源码。能数值验证就验（有限差分比梯度、golden 逐行对齐）。
2. **口径**：理由有没有超出事实范围（「已全清」「都支持」是否只对某个目录、语言、分支成立）。
3. **结构**：fence 配对、表格列数一致、行内反引号配对、CRLF 计数 == 换行数、无 BOM、python 块 `compile()` 通过。
4. **越界**：有没有改到不该改的行、有没有超出「修报告问题」的重排/扩写；风格是否与同文件既有写法一致。

## 样本错误（实测抓到）

- 「返回 `(g1, g2, None, None)`，与 forward 入参一一对应」——forward 5 个入参，断言自相矛盾。
- yaml 字段三连错：`triton_name` 应为 `<模块>.<类名>`（只有 `triton_api_type` 等于注册名）、路径应为 `shapes.dim_numbers.values`、「单例阈值 [0.95,0.98]」实为单例 0.98 / 平均 0.95。
- 公式只修了转置、漏了 chunk 内衰减项（`v_new` 存的是衰减前的值）。
- 「同一内核两名」修错方向：文档固定用法与源码注释都是 fallback，却统一成了另一个词。

## 报告写法

把「确认无问题」与「复核后修正」分成两节；每条带原始扫描判定（severity/rule/category/标题/命中原文/建议/影响）、结论与置信度、证据、实际 diff；口径更正要单独列。
