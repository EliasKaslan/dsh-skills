# 订阅额度 → 可完成任务数（换算方法与取数）

适用于用户问「同样 $X 预算，某订阅一个月实际能做多少任务」。不适用于纯 API 单价对比（→ SKILL.md「成本核算」）。

## 为什么不能用 $X ÷ 单价

订阅不按 token 计费，按加权算力（不同模型权重不同）计量；而且同一 $X 在三家常落在不同命名档。用挂牌单价乘 token 数会系统性高估贵模型（3–10 倍）。

## 步骤

1. **对齐档位**：先查每家当前档位命名与价格（会改名），确认「$X 买到的是哪一档」。不要拿 A 家的次旗舰对 B 家的旗舰。
2. **认清额度性质**，三种完全不同：无 5h 限制、只周限额；5h 窗 + 周窗双限额；算力制、5h 刷新直到周上限。
3. **找计量锚点**（社区实测，一律标注非官方）：GitHub issue 的计量实验（「1% 窗口 = X token」「Y 小时吃掉 Z% 周额度」）；论坛/X 逐请求账本（5h 窗 token、周 token、API 计价三件套）；官方论坛的「几天打空周额度」报告，用来给账本打折——账本常高估 2–3 倍。
4. **换算**：月任务数 = 周 token 容量 ÷ 单任务 token × 4.3；再与 wall-clock 上限（单任务分钟数 × 8h × 21 天）取小。单任务 token 用同 harness 的 AA tokens/task，跨 harness 差 2–4 倍。
5. **输出区间**：两派实测差 2–3 倍是常态；只报区间 + 口径脚注，不报单点。

## 判据与坑

- 「固定小题套件」口径与 token 口径不可混算，必须换算到同一 task 定义。
- 账本常滞后一代模型：拿到上一代同系列的实测，明确写「未覆盖当前型号」。
- 缓存权重是订阅计量的核心：不要用 $ 反推 token。
- 长上下文重定价：若模型对超阈值请求「整条」翻倍计价，长会话单位成本翻倍，预算换算要分短/长上下文两套。
- 官方通常只给 `N× Pro`；credits 属超量加购而非配额，这类一律标「未公布」。

## 交付格式

表：模型 × 订阅档 | 月任务数区间 | 折算 $/任务 | 任务节奏上限；单列「未取到」与「冲突值」。结论落到「买任务量 / 买一次做对的概率 / 买帕累托折中」三选一。
